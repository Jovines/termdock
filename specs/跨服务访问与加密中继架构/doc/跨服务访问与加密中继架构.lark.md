# Termdock 跨服务访问与加密中继架构

## 一、目标与设计状态

Termdock 拟将应用层端到端加密作为统一访问基础，覆盖普通直连和跨服务中继；不把 HTTPS 作为内容保密的唯一保障。同时提供通用的远程服务访问能力：用户通过手机 PWA 连接一个入口服务，即可在当前窗口浏览并打开其他已授权服务的 Session。该能力由服务连接、路由、中继、身份授权及加密通道共同提供，工作组是其使用方之一。

当前实现已加入通用终端访问、CLI/macOS 中继生命周期、Noise 加密通道、设备授权及邀请入口。本文保留总体设计与验收要求；已实现配置和限制见 `src/server/federation/README.md`。真实 iOS 前后台、macOS 休眠与签名安装包验收仍需相应设备环境，不将单元测试和桌面构建等同于这些验收。

## 二、角色与两种访问路径

| 角色 | 职责 | 是否必须持续在线 |
| --- | --- | --- |
| 手机 PWA | 展示界面，验证目标身份，处理输入与输出，作为加密端点 | 使用期间在线 |
| B：入口服务 | 提供手机入口、路由目录和通道转发 | 是 |
| A：中继 | 同时连接 B、C，将获授权的通道在两条连接间转发 | 使用经 A 的路径时必须在线 |
| C：目标服务 | 管理真实 Session、终端进程和目标访问权限，作为加密端点 | 是 |

直接可达时：`手机 → B → C`。

B、C 无法互通，但 A 能连接两者时：`手机 → B → A → C`。建立连接的方向为 `手机 → B`、`A → B`、`A → C`；连接建立后双向传输，所以 B 可以通过 A 主动建立的连接向 A 发出转发请求，不要求 B 能新建到 A 的入站连接。

[查看连接拓扑图源](../diagrams/01_connection_topology.mmd)。

A 可以是 macOS 客户端，也可以是独立 CLI 常驻中继。Mac 休眠、退出或断网会使依赖它的路径失效。若没有直接路径或其他获授权中继，不能继续访问 C。第一版支持直接连接以及一个显式中继 A，不提供自动递归发现的任意多跳网络。

## 三、通用能力分层

| 层 | 责任 |
| --- | --- |
| 产品入口 | Mac、CLI、Web/PWA 管理连接、配对、共享范围及状态 |
| 身份与授权 | 验证设备和服务身份，签发、检查和撤销访问许可 |
| 服务目录与路由 | 维护服务身份、可用连接、直连或中继路径、能力版本 |
| 通道传输 | 长连接、逻辑流复用、背压、心跳、限流和错误传播 |
| 加密会话 | 在实际客户端与目标服务之间完成身份绑定和加密 |
| 业务适配 | Session 列表、终端画面、输入、工作组以及后续文件能力 |

Mac 和 CLI 共享连接与中继核心，避免将通用实现绑定到 Electron 窗口。Web/PWA 提交配置意图，长期凭据和路由运行状态由相应服务或中继管理。

Session 始终运行在所属目标服务。入口服务不复制终端进程，也不因查看远端终端而获得目标机器上的任意执行权限。路由只接受已登记的目标身份及允许的业务通道，不开放任意 URL 或任意 TCP 端口代理。

## 四、发现、配对和共享

“Mac 已经登录 B、C”只说明 Mac 自己具备访问条件，不意味着所有连接 B 的手机自动获得 C 的权限。

手机普通直连必须与原来的输入密码登录流程相同，不增加二维码、指纹或配对步骤。内部通过 OPAQUE 密码证明认证双方身份并保存设备授权，之后建立 Noise 通道；二维码和邀请链接只用于主动分享其他设备或服务。无密码模式保留开放语义，首次固定身份依赖 HTTPS，不能宣称这一首次信任独立于 TLS。

跨服务共享流程如下：

1. A 与 B、C 建立经过认证的连接；明确选择允许 A 为 B 中继到 C。
2. C 的管理员批准共享范围；B 只公布获准展示的服务入口，不预先同步全部 Session 名称、目录和任务内容。
3. 手机通过 B 发现 C，首次使用时经可信二维码、已验证设备签署的介绍或独立指纹确认 C 的身份。仅接受 B/A 返回的未验证公钥不能建立可信目标身份。
4. C 向手机的设备身份授予访问权限。可设计由已获授权管理员批准的便捷配对，不把 Mac 的整套登录 Cookie 或长期管理员令牌复制给 B、手机。
5. 手机在加密通道内获取 C 允许展示的 Session 列表并打开终端。

建议用稳定 `serviceId + sessionId` 标识远端 Session；服务地址变化不应改变身份。现有按 origin 编码的远端标识需要兼容映射，迁移时不能丢失原有工作组成员或把相同 Session ID 的不同服务合并。

路由广告带发布者身份、目标身份、有效期和协议能力；过期或中继离线时撤销可用标记。路线切换只改变传输路径，不能改变目标身份或绕过 C 的权限验证。第一版重建业务流并重新校验，不承诺无缝切换。

## 五、终端打开与交互

手机向 B 请求通往 C 的逻辑通道。B 选择经授权的直连或中继路径，A 仅在已登记连接之间转发。通道建立后，手机与 C 完成加密握手及权限检查，再发送 Session 打开请求。

C 返回当前终端状态及连续输出；手机在当前窗口的终端组件中渲染。需要区分“恢复当前屏幕”和“获取完整历史滚动记录”，历史范围取决于 C 的现有存储与授权，不因增加中继而承诺无限历史。

[查看加密访问时序图源](../diagrams/02_encrypted_access.mmd)。

只读访问不能向目标发送键盘输入，也不应因手机屏幕变小而改变所有客户端共用的 PTY 尺寸。交互模式必须复用或明确现有的终端尺寸管理规则；多个客户端同时操作时，需呈现控制权及冲突策略。

通道应具备逻辑流隔离、最大帧限制、有限队列和背压；慢速手机或大文件传输不能导致中继无限缓存或阻塞其他终端。断线后保留最后画面并明确标注已过期。重新连接按序号恢复输出或重新获取快照，拒绝旧加密帧；未确认的输入不得自动重放。已确认输入的含义也应明确为目标收到或写入 PTY，不宣称命令已经执行完成。

## 六、加密与信任边界

### 6.1 两层保护

无论客户端直连本机/远端服务，还是经过入口及中继，业务数据都必须先在客户端完成应用层加密，由实际目标服务解密。直连时端点为“客户端与所访问的服务”，访问 C 时端点为“客户端与 C”。

每段网络连接仍使用经验证的 HTTPS/WSS。TLS 保护一段连接上的传输，不能让终止该连接的代理天然看不到明文，因此还需要应用层的端到端保护。[协议背景：IETF TLS](https://www.rfc-editor.org/rfc/rfc8446)。

访问 C 时，应用层加密端点是手机和 C；B、A 转发密文，不能获得此会话的内容解密密钥。保护范围包括所有受保护业务载荷：终端输出及输入、Session 列表和详情、任务与工作组内容、文件路径及文件内容、设置、管理请求和返回值。无需敏感内容的引导、健康检查及最小路由元数据单列为公开面，并逐项审查；不能把普通 REST 接口遗留为明文旁路。路由仍需要有限的目标标识和通道标识；中继可以观察时间、流量大小和连接关系，不能宣传为匿名网络。

### 6.2 协议要求与选型门槛

采用 `@chainsafe/libp2p-noise` 17.0.0 的 Noise 实现与 Ed25519 身份，密码引导使用 `@serenity-kit/opaque` 1.1.0；不自创握手及密码算法。浏览器与 Node 真实 WebSocket 通道已验证，Electron 构建通过，签名安装包的设备验收另行记录。连接在 60 分钟或任一方向 512 MiB 上限到达时关闭并重新握手，不把关闭重连描述为库内原地 rekey。

选型必须覆盖双向身份验证、握手记录与目标身份绑定、临时会话密钥、方向分离、认证加密、nonce 唯一性、重放防护、密钥更新、重连后的旧会话隔离和协议版本防降级。不得将只支持逐段 TLS 的旧节点静默标为端到端加密连接。

加密握手验证客户端身份，C 再验证其操作权限；加密不代替授权。中继路由票据也不等于目标访问令牌。对有副作用的输入与请求，不启用可能被重放的早期数据机制。

### 6.3 防御 HTTPS 解密代理

设备安装并信任抓包代理的根证书后，代理可能分别终止客户端和服务端的 TLS 连接。架构不能仅凭浏览器 TLS 验证成功，就认定业务内容不会被中间设备读取。

应用层目标身份必须由独立配对得到的可信公钥或可信身份链验证，不继承系统新增根证书的信任。可信客户端与目标服务完成应用层加密后，即使代理解开 HTTPS/WSS，也只能观察外层封装、必要元数据和应用密文；替换目标握手或修改密文必须被拒绝。

该保证有两个前提：客户端代码和目标端点未被控制，且首次配对没有被攻击者替换。通过相同受拦截页面展示一个指纹，再在同一页面点击确认，并不能独立解决首次信任。

### 6.4 PWA 的代码来源边界

若 PWA 由 B 提供，B 能决定浏览器执行的前端代码。被攻陷的 B 可提供恶意脚本，在加密前读取输入或在解密后读取输出。因此该部署仍信任 B 提供正确的客户端代码，即使正常运行的 B 服务端只处理密文。

浏览器不可导出密钥有助于限制直接导出，但不能阻止具备相同代码执行权限的恶意脚本调用密钥。CSP、依赖治理和代码审计降低风险，不消除提供代码的服务所处的信任位置。[依据：W3C Web Cryptography 安全注意事项](https://www.w3.org/TR/webcrypto/)。

因此，“HTTPS 可被解密并主动改写时仍保护内容”的完整目标，必须同时解决客户端代码可信加载问题。签名原生客户端需验证安装来源和更新签名；独立域名 PWA 只是移动了代码信任来源，仍走受拦截 HTTPS 时并不天然满足该目标。

普通浏览器 PWA 首次从可被修改的网络下载代码，无法仅靠该页面内的 JavaScript 校验程序自证安全。CSP、SRI、Service Worker 缓存都不能单独建立独立于被修改页面的信任根。需评估由可信应用包装/分发的客户端、独立验证的代码更新机制，或明确限定 PWA 的安全承诺。未解决该问题前，不得宣称纯 PWA 能防御主动替换前端的 HTTPS 抓包代理。

### 6.5 端点与静态数据

C 必须处理明文才能运行终端；设备被完全控制或目标服务被攻陷，不在中继内容保密的保护范围内。PWA origin 改变或存储被清理时，设备身份可能需要重新配对。

私钥存储、备份、恢复与轮换需要平台化实现。原生端评估系统密钥库，服务端使用严格文件权限及可选外部密钥保护，PWA 评估浏览器密钥存储及恢复流程。

传输加密不自动加密 C 的终端历史、文件、工作组副本或备份。静态加密与工作组消息加密需要独立设计，不能沿用“整个服务已加密”的笼统表述。

## 七、多维授权体系

### 7.1 授权记录

每条授权至少包含以下维度。路由可达不代表获得访问权，加入工作组也不自动得到对应成员的终端权限。

| 维度 | 含义 | 示例 |
| --- | --- | --- |
| 主体 | 哪个用户、设备或服务身份获得权限 | 已配对手机设备 |
| 目标服务 | 哪个稳定服务身份签发和执行授权 | C 的 serviceId |
| 资源范围 | 整个服务，或明确列举的 Session | 整服务 / Session S1、S2 |
| 操作集合 | 所有能力，或明确的读、写、管理操作 | 全部 / 只读 / 读写 |
| 生命周期 | 到期、撤销、授权版本 | 持续至撤销 / 指定有效期 |
| 委托规则 | 能否为其他主体签发授权及其上限 | 不允许 / 明确范围内允许 |
| 可选条件 | 被允许的入口、中继或其他约束 | 仅允许经 B 和 A 访问 |

主体身份与设备绑定关系需要明确：若授予单台手机，其他新设备不能仅凭相同入口登录状态继承授权。服务地址不是身份，路径切换也不能切换目标或扩张权限。

### 7.2 资源与操作的组合

| 授权方式 | 允许能力 | 不自动附带 |
| --- | --- | --- |
| 整服务完整授权 | 服务的所有业务和管理能力，包括全部现有及后续 Session、文件、设置、授权管理 | 其他独立服务的权限；平台尚未实现的能力 |
| 整服务自定义授权 | 在全服务范围应用指定操作，例如全部 Session 只读 | 未勾选的写入和管理能力 |
| 指定 Session 只读 | 这些 Session 的最小必要元数据、当前画面、获准历史及实时输出 | 输入、改变共享 PTY 尺寸、终止、文件浏览、服务配置 |
| 指定 Session 读写 | 上述读取能力，加输入及明确获准的交互控制 | 终止/删除 Session、服务管理及独立文件 API |
| 指定 Session 管理 | 为选定 Session 单独授予终止等管理操作 | 创建其他 Session、改变整个服务设置 |

整服务完整授权对应明确的通配能力 `*`：覆盖该服务当前及未来新增能力，是持续的管理员级信任。界面必须明确这一含义；需要固定能力集合时，选择“自定义授权”，不要把两者混为一谈。完整授权包括授权管理，因此允许在该服务范围内管理其他授权；不应以普通“读写”标签隐藏这一权限。

“读”“写”是易懂的产品预设，底层使用明确动作，例如 `session.view`、`session.input`、`session.resize`、`session.terminate`、`file.read`、`file.write`、`service.configure`、`authorization.manage`。这些动作由目标端策略映射到实际 API。细粒度授权下，每个新接口必须登记资源与动作，缺少登记时默认拒绝；整服务管理员保留明确的全部业务能力语义。

Session 读写可调用终端输入，这意味着主体可能执行该终端操作系统用户有权运行的命令，包括读取文件、删除文件和访问网络。API 权限隔离不等于操作系统沙箱；即使未授权独立文件 API，也不能宣称已阻止通过 shell 读写文件。需要真正限制机器资源时，应另行使用受限系统账户、容器或命令环境。

只读用户也可能在终端输出中看到密钥等敏感信息。“只读”限制修改行为，不代表输出经过脱敏。

### 7.3 权限计算与委托

第一版建议采用“默认拒绝 + 显式允许”的模型。同一主体的有效目标授权取并集；资源范围、操作、有效期及条件必须在同一条授权内同时满足，不能把两条授权的资源和动作交叉组合。若同时存在整服务完整授权和某个 Session 只读授权，完整授权仍生效，较窄授权不会把它降为只读。界面展示最终有效权限及授予来源；降低权限需要撤销或收窄原有宽授权。

每个请求的最终权限还受目标服务策略和通道条件约束。中继许可只允许转发，并不增加目标权限。普通查看和读写授权不允许再授权；明确委托时，子授权不得超过父授权的目标、资源、动作、有效期及条件。撤销父委托同时使依赖它的子授权失效。

C 持有最终决定权，基于已完成加密身份认证的实际主体进行验证，不能使用 B 或 A 的管理员身份替手机代办业务请求，否则会丢失手机级权限隔离。

### 7.4 撤销、审计与错误

撤销后目标服务关闭相关活动流并拒绝重连；已经交付给客户端的历史数据无法收回。离线节点无法保证立即接收撤销通知，需定义短期凭据、目标在线验证和最大撤销生效窗口，不笼统承诺瞬间全球撤销。

B/A 仅记录必要的路由和错误元数据，不记录终端正文或凭据。C 记录实际授权主体、资源、动作、授权来源及结果；是否保存命令正文另行制定隐私策略。

界面区分目标不可达、中继离线、授权不足、目标身份变化、协议不兼容和加密失败。安全错误不得降级为明文。正常使用只需显示“C · 经 A 中继”和“只读 / 读写 / 完整权限”，提供入口查看具体有效范围。

## 八、工作组接入与兼容

工作组成员点击行为调用通用 Session 打开接口；服务目录中的 Session 同样可以打开，不要求先加入工作组。加入工作组与授权终端访问是两个不同动作。

已有工作组副本和消息同步保持明确兼容边界。后续可以复用通道迁移协作传输，但服务参与者仍是消息的合法接收端；工作组消息的加密端点和密钥分发不能直接套用“手机与 C”的会话模型。

升级通过能力协商展示支持项。旧服务仍可参与原有协作，但如果不支持新加密通道，远程终端入口应明确不可用，不能伪装成已保护连接。迁移过程保留旧标识映射、工作组关系和可回滚的配置版本。

## 九、分阶段实施与验收

| 阶段 | 交付范围 | 核心验收 |
| --- | --- | --- |
| 0：协议与安全原型 | 身份、配对、授权模型及加密库验证 | 手机与 C 经不解密的 B/A 成功建立会话；身份替换、篡改和重放被拒绝 |
| 1：通用只读访问 | 服务目录、直连与单中继、终端查看；Mac 和 CLI 共用核心 | 人为阻断 B 与 C 直连，手机仍经 A 查看 C；A 断线后准确提示；只读不修改 PTY 尺寸 |
| 2：交互及工作组 | 输入权限、终端控制、工作组点击接入 | 未授权输入被 C 拒绝；断线输入不重放；同名及同 ID Session 不串服务 |
| 3：通用文件与运维 | 文件权限、配额、撤销、路由切换和恢复 | 大文件不拖垮终端；撤销终止活动流；路径切换不降低加密和授权要求 |

第一阶段面向用户的远程访问必须具备身份验证与端到端保护，不能先交付无保护转发，再把安全性留到后续补齐。跨服务工作组消息迁移和静态存储加密另列范围。

安全验收必须增加两组场景：一是安装受信任抓包证书，分别验证普通直连与中继时业务载荷仍为应用密文，并验证身份替换、握手篡改和旧帧重放被拒绝；二是主动替换 PWA 引导代码，验证受支持的可信客户端是否拒绝被替换代码，普通 PWA 无法满足时明确记录限制。

授权验收覆盖整服务完整授权、指定 Session 只读/读写、未授权 Session 枚举、跨 Session ID 越权、宽窄授权并存、过期与撤销、委托扩权和活动流降权。通过真实通道及目标 API 测试，不能只检查前端按钮是否隐藏。

发布前覆盖真实手机 PWA 的前后台切换、Mac 休眠、CLI 常驻运行、多个客户端、丢包重连和低速网络。性能指标在原型测量后制定，不预先给出无证据吞吐量或并发承诺。

## 十、实施前需要收口的决策

- 选择并审查加密协议及实现，确认目标浏览器支持和密钥生命周期。
- 确定抵御主动 HTTPS 内容替换所需的可信客户端分发方案；明确纯 PWA 未建立独立代码信任根时的安全上限。
- 确认首次配对、管理员批准、丢失设备撤销及身份恢复的用户流程。
- 确认完整授权通配语义、只读/读写动作清单、委托撤销窗口及多客户端控制规则。
- 确认既有远端标识的迁移、CLI 命令、配置格式及流量限制。

这些决策影响实现细节，不改变总体结构：客户端通过一个入口，沿直连或显式中继路径访问目标；目标保留终端所有权和最终授权，加密会话独立于传输路线。
